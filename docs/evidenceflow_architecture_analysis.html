一、项目当前设计与完成程度

EvidenceFlow 是一个 评测驱动（evaluation-first）的本地学术 RAG 系统。目标不是"堆出一个 RAG demo"，而是让每一层设计都可解释、每一项决策都有实验证据、每一个已知问题都有明确归因与处置结论，并拒绝在证据不足时增加技术复杂度。当前代码已完整实现 Phase 1（Local RAG） 全部链路。

四、RAG 核心设计三问

4.1 Embedding 怎么设计的

决策做法为什么
模型选型BAAI/bge-m3，仅用 dense（1024 维）中文→英文跨语言检索是核心场景，bge-m3 多语言第一梯队；sparse/colbert 引入需对应失败证据
归一化Provider 边界显式 L2 归一化（不用库默认）拦截零向量/NaN/Inf；统一 numpy.float32→Python float；Fake 测试遵循同一合同
文档=Query同一模型、同一向量空间Chunker 也复用同 tokenizer，保证 chunk_size 的 token 语义与模型一致
编码细节切分 add_special_tokens=False；Query 不 strip 不改写512 表示纯正文 token，不含 CLS/SEP；原文直传避免信息丢失

归一化后 dot(a,b)==cosine(a,b)，Chroma 的 cosine distance 可直接转 similarity = 1 - distance，语义无歧义。

4.2 Chunk 怎么设计的

参数值依据
chunk_size512论文段落级语义单元；远低于 bge-m3 的 8192 上限，避免截断
chunk_overlap64（12.5%）固定比例使 C256/C512/C1024 三组实验只变一个变量
step448（派生）= chunk_size - overlap，不是独立配置

为什么按 Token 而非字符：Embedding 有硬 token 上限；中英文字符密度差异极大，按字符切会导致语义密度严重不一致。
为什么固定滑窗而非语义切：刻意保守——完全确定性、可复现、可审计，是做评测基线的正确起点。代价是 Chunk 会跨 section/正文-References 边界（10/10 篇实测），但已如实记录、不改 Runtime。
chunk_id 设计：SHA256(document_id + chunk_size + overlap + chunk_index + SHA256(解码文本))，配置/内容变了 ID 就变，可做增量去重与失败归因；但 Gold 不用 chunk_id 判据（用 document_id+页码+原文锚点），使同一评测集可复用于三组 chunk 实验。

4.3 Top-K 是多少、为什么

系统里有三个不同的 K，这是面试最容易说混也最该说清的点：

参数值作用为什么
multilingual_candidate_top_k10每路 Dense 候选深度宽召回，给 RRF 融合留空间；10 是召回与噪声的折中
multilingual_final_top_k5融合后返回给 Context 的数量受 4096 token 预算硬约束：5×512≈2560，留标签/文件头/分隔符余量
top_k (Settings)5单路 Dense 默认深度单独使用时的默认
  • Final=5 的三层约束：① 预算硬约束（Context Builder 按完整渲染文本计数，6 条就逼近上限）；② 噪声约束（Top-5 后相关性断崖，Hit@10 只比 Hit@5 多 17.5pt 但多为噪声）；③ 中间迷失（lost-in-the-middle）。
  • RRF k=60：RRF 原始论文（Cormack 2009）经验常数，平滑排名贡献，避免两路余弦分数不可比。
  • Equal RRF（1.0/1.0）而非加权：早期旧 Holdout 支持翻译分支 1.1，但新的 40 题 Fine-grained Holdout 没复现优势，且规定证据优先级以 Fine-grained 最高。选择更简单、在独立分布上更稳定的 Equal RRF，并明确写"这不是全局最优声明"。

六、面试高频问题速答

Q：为什么不用 LangChain / LlamaIndex？
A：目标是理解并可解释每一层，不是堆 demo。自研让数据合同完全可控（页码溯源、chunk_id 稳定性、Gold 匹配），框架里这些是黑盒，且会诱导"无证据地加技术"。

Q：为什么用 Chroma 而不是 Faiss / Milvus？
A：Phase 1 单机本地、361 Chunk。Chroma 提供持久化+metadata 过滤+开箱 cosine，够用零运维；用 VectorStore 抽象隔离实现，换库只加 adapter。

Q：为什么用 RRF 而不是把两路分数归一化后加权？
A：两路余弦分数不可比（不同 Query 文本→不同分布），归一化会引入分布假设。RRF 只用排名，天然免疫尺度问题。

Q：为什么不上 Reranker？
A：Reranker 解决"排序失败"，当前只有 7 个；而候选生成失败有 12 个——排序不是主瓶颈，且 12 个失败 reranker 也救不回（无法重排不在候选池的结果）。正确顺序：先扩候选（BM25 已验证有效），再重排。

Q：怎么防止引用幻觉？
A：四层防护——① Prompt 只允许 Context 中存在的 [Sx]；② Parser allowlist 严格校验；③ answered 状态必须至少一引用否则报错；④ 来源只能来自 Context 映射，不从模型文本推断。

Q：最大短板是什么（诚实回答）？
A：① Top-5 命中仅 47.5%，12/40 候选生成就失败；② 多文档题 4/4 全灭；③ 表格/公式/图注结构信息基本丢失；④ 评测集仅 40 题；⑤ 还没有生成质量评测。

Q：下一步做什么？
A：唯一推荐——augmented_candidate_reranking 实验：在 Dense+BM25 增强候选池上重排，看能否把已验证的候选覆盖增益转化为 Top-5 命中。实验完成前不改 Runtime、不升级 PROJECT_SPEC。

七、30 秒讲这个项目（面试版）

我实现了一个本地学术 RAG 系统，10 篇论文 145 页，切 361 个 Chunk，用 BGE-M3 做 1024 维向量、Chroma 存储。最有意思的不是技术栈，而是方法论：我先建了 40 题带原文锚点的冻结评测集，测出 Top-5 命中 47.5%，把 21 个失败题分成候选生成失败 12、排序失败 7、切分失败 2。针对最大的 References 污染做了隔离实验——过滤 32 个槽位只救回 1 题、反而误伤 1 题，结论是不上线。又做了 BM25 增强实验，候选覆盖 65%→77.5% 且零回退，但 add-only 不解决排序，判定"暂不集成"，下一步做重排。整个项目我始终坚持：没有评测证据，不增加技术复杂度。
